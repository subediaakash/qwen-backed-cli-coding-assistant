A lesson in agent harnesses

Inside the Qwen Review Harness

How a small local model becomes a code reviewer, and why most of the work is the code around it.

The model The harness (our code) Tools
1 · Three words

Model, harness, agent

Model

Reads messages, writes one reply. It can ask for a tool, but it can't run anything or remember anything.

Harness

All the code around the model: the loop, the tools, the safety checks, and the checks on its answers.

Agent

Both together, working on a goal. The model picks the next step; the harness decides what's allowed and does it.

model + harness = agent

2 · The loop

Every agent is a loop

  1. Send

    The harness sends the whole conversation to the model.

  2. Decide

    The model replies: "call GitDiff", or "I'm done".

  3. Run

    The harness checks the request and runs the tool.

  4. Remember

    The result is added to the conversation.

Repeat until the model says it's done, or until it runs out of steps (15 by default). Then one last call, with no tools, writes the answer.

3 · What is a tool?

A tool is a description plus a function

The model never sees our code. It only sees a name, a description and the arguments a tool takes. When it wants one, it replies with a small JSON request. The harness runs the real function and sends the result back as a new message.

What the model sees 
{
  name: "GitDiffFile",
  description: "Show the unified diff
    of a single file changed by the PR.",
  parameters: {
    base: string,  // required
    head: string,
    path: string   // required
  }
}
What the model replies 
tool_calls: [{
  name: "GitDiffFile",
  arguments: {
    base: "review-test~1",
    head: "review-test",
    path: "src/test/cart.ts"
  }
}]
What the harness does

Checks the tool is allowed and the path stays inside the project, runs git diff, cuts the result down if it's too long, and adds it to the conversation.

The description is a prompt too. "Call this first, then GitDiffFile" in the GitDiff description is how the model learns the order.

6 · Is it any good?

Measure it with evals

A normal test checks that the same input gives the same output. The model answers differently every time, so we use an eval: plant known bugs, run the reviewer several times, and count how many it finds.

- for (let i = 0; i < items.length; i++) {
+ for (let i = 0; i <= items.length; i++) { ← bug 1: one step too far
- if (percent < 0 || percent > 100) throw … ← bug 2: check deleted
+ if (percent < 0) throw …
- const items = await fetchItems();
+ const items = fetchItems(); ← bug 3: missing await
Bugs shown as edits 9 / 9 found in 3 runs, 0 false alarms
Same file, shown as new 6 / 9 missed bug 2 every time

Bug 2 is a deleted line. When the reviewer can see the deletion, it catches it. When it can't, it never does. What the model sees decides what it can find.

7 · Going further

What bigger agents add

This reviewer is the smallest honest version of an agent. Tools like Claude Code or CodeRabbit run the same loop, with a lot more harness around it:

  • Context managementSummarize or drop old messages when the window fills up, instead of just cutting tool results.
  • Stronger guardrailsPermissions, sandboxes, and asking the user before anything risky like writing files or running commands.
  • Bigger evalsHundreds of real cases instead of three planted bugs, run on every change to the prompt or the harness.
  • More than one agentOne agent hands a sub-task to another, which starts with a clean context and returns only the answer.
